## Что изменено

- Добавлена повторяемая миграция статуса в staging и mart; старые строки получают `shipped`.
- В mart сохраняются события продажи и возврата. Сумма и количество возврата отрицательные.
- Старый CSV без статуса поддерживается; неизвестные статусы отклоняются.
- Скачивание и проверка CSV происходят до изменения БД.
- Данные дня в staging и f_sales заменяются целиком, в том числе для исправленного или пустого инкремента.
- Затем пересчитывается вся неделя изменённого дня. Повторная загрузка не добавляет строки к прежнему результату.
- Миграция, замена staging, обновление справочников и обеих витрин выполняются одной транзакцией: ошибка откатывает изменения.
- Вместо удаления справочников используется UPSERT.
- Недельная витрина строится из f_sales и включает исторические продажи, доступные в учебном контейнере.
- Удалён отдельный weekly_dag: пересчёт недели зависит от успешной загрузки дня.
- SQL находится рядом с DAG и читается через абсолютный путь относительно Python-файла.
- report_id сохраняется в Airflow Variable и используется всеми последующими днями.

проверить report_id и дату, а не пропускать день как будто он загружен.

## Принятые правила расчёта

- Зерно retention: неделя × item_id. Клиент классифицируется внутри этого разреза.
- `new`: один заказ со статусом shipped; `returning`: более одного.
- При наличии CSV-поля `order_id` считаются уникальные order_id. Иначе используется
  `uniq_id` как ключ заказа в учебных данных. **Это допущение нужно сверить с реальным CSV**:
  если uniq_id — идентификатор товарной строки, нужен настоящий идентификатор заказа.
- Продажа и возврат с одним uniq_id сохраняются отдельно; конфликтующие записи
  с одинаковым ключом (uniq_id, status, item_id) отклоняются вместо произвольного выбора.
- Для старых строк f_sales без ключа заказа используется id строки; это предполагает
  одну историческую строку заказа на item_id. Утраченную детализацию восстановить нельзя.
- Доход группы — сумма продаж и возвратов её клиентов за эту же неделю.
- Клиент только с возвратом не становится new/returning: учитывается в refunded_customer_count
  и customers_refunded. Сумма такого возврата остаётся в f_sales; отдельного поля суммы
  возвратов в заданной девятиколоночной retention-схеме нет.
- `refunded_customer_count` — число клиентов с возвратами; `customers_refunded` — число
  событий возврата. Для частичных/повторных возвратов нужен отдельный ключ события источника.
- Период — понедельник включительно, следующий понедельник исключительно.
- period_id = ISO-год × 100 + ISO-неделя (например, 202053). Это отличает недели разных лет
  и сохраняет заданный тип integer. При требовании ревьюера хранить только 1–53 нужно
  согласовать отдельное поле года, иначе многолетние данные будут смешиваться.
- item_id сохраняется в смысле исходной модели. Если это товар, а не категория,
  для настоящего разреза категорий понадобится справочник соответствий.

## Проверка этапа 3 в Airflow/PostgreSQL

1. Успешно загрузить день D. Сохранить строки staging за D, f_sales за D и retention
   за его неделю (сравнивать бизнес-поля, без технического serial id).
2. В Airflow Graph очистить **все три задачи** запуска D с подтверждением повторного выполнения.
   После повторного успеха число строк и значения бизнес-полей должны совпасть.
3. Получить восстановленный инкремент по тому же report_id и дате D, повторить запуск.
   В staging и f_sales должны остаться только актуальные данные D, а retention —
   соответствовать обновлённой неделе. Изменение serial id после пересборки нормально.
4. Проверить контрольные запросы из `tests/checks.sql`.
5. Для проверки rollback в тестовом окружении вызвать ошибку после удаления staging:
   транзакция должна сохранить прежние staging и обе витрины.
